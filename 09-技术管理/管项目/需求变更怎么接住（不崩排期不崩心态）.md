# 需求变更怎么接住（不崩排期不崩心态）

## 一句话速记

需求变更不是坏事——怕的是**无代价的变更**。每次变更，你要做的不是"接"或"拒"，而是**把变更的成本翻译成对方听得懂的语言**（时间/资源/质量），让 TA 做选择。三个动作：① 理解变更背后的真实需求（TA 为什么要这周五？真急还是随口一说？）；② 量化变更成本（"你要的这个功能需要拆掉已写完的 X、重做 Y，需要多 2 周"）；③ 给出选项，让 TA 选（砍别的 / 加时间 / 给资源）。

## 通俗解释（5 分钟版）

```
致命处理方式：
  PM："客户说必须要这个功能下周一上线。"
  你："来不及啊！"（你在谈感情）
  PM："必须来及！客户都发火了！"（TA 在施压）
  → 争执无果，最后勉强答应 → 团队加班到崩溃 → 质量出问题 → 返工更多

有效处理方式：
  PM："客户说必须要这个功能下周一上线。"
  你："好，我们来看看怎么做到。目前排期上这周和下周都已经满了。
      如果要加这个，有三种可能：
      ① 砍掉已计划的 Y 功能（留到 V2 做），可以赶上周一
      ② Y 功能不砍，但只能下周三上线
      ③ 加人——找老王支援，但 TA 需要 2 天熟悉代码，
         能赶上周一但质量会比正常低
      你倾向哪个？"
  PM 做选择——TA 选的方案，TA 一起承担后果。
```

## 关键细节

### 第一步：分辨"真急"还是"随便说说"

```
对方说"这个很急"时，追问：

"如果我理解对，你的意思是：
  ① 这个功能对某个客户确实是必须的，没有就流失
  ② 这是老板要求的
  ③ 这是你觉得最好这周做但不是非本周不可
  ④ 这是下季度规划里的，但现在提前想到就先说了

你指的是哪种？"

→ ③④ 占了"很急"的大多数。真的 ① 很少。
  真到了 ① 的程度，让对方带你去见客户/老板亲口确认。
```

### 第二步：量化变更成本——用"代价"代替"不行"

```
不要说"这个技术上做不了"——通常只是"在这个时间做不了"。

任何时候给 3 个选项：

1. 砍范围
   "如果要下周一上线，我只能保证核心功能，边缘 case 下版补。"

2. 加时间
   "如果完整功能都要，下周三可以。"

3. 降质量
   "下周一可以全上，但跳掉灰度、跳掉降级方案，
    上线风险会高一些。你接受吗？"

这三种选项的威力在于：
  - 你不是在拒绝 TA，你是在帮 TA 解决问题
  - 每个选项都有代价，TA 必须自己做取舍
  - TA 选的方案，后续出问题 TA 没法甩锅
```

### 第三步：保护团队——你是挡板和翻译器

```
不要做的事：
  ✗ PM 说加需求你就转身拍给团队："大家辛苦一下周末来吧。"
  → 你是 PM 的传话筒，不是 TL。TL 的职责是在消化压力后
    给团队可操作的方案，不把原始焦虑传导下去。

✓ 你不是传话筒，你是翻译器：
  外部压力 → 你消化 → 翻译成团队能执行的方案
  你面对 PM 时可以说"我们再努力一下"，转身面对团队时说
  "我们一起对一下优先级，看看怎么安排最合理"
```

**保护好团队的节奏**：

```
规则 1：一次迭代里只接受一定比例的变更（如 20% 时间）
  超过这个比例 → 改排期而不是挤压团队

规则 2：任何变更都走一个轻量流程（哪怕只是群聊里说清楚
  改什么/为什么/影响什么）

规则 3：如果团队连着两次被要求加班赶变更 → 你的问题，
  你没有挡住应该挡住的东西
```

### 变更来了先问的三个问题

```
1. "这个变更比已经排好的那些更重要吗？"
   → 如果比已排期的都重要 → 砍已排期的

2. "这个变更是因为之前没想清楚，还是外部条件变了？"
   → 没想清楚：这是需求阶段的问题，改进下次的需求评审
   → 外部变了：合理，接受

3. "如果不做这个变更，最坏的结果是什么？"
   → 很多"紧急变更"不做也不会死。
      如果对方答不上最坏结果，说明不够紧急。
```

## 延伸追问

- **Q：老板直接提的变更怎么处理？**
  → 一样的流程。"老板，我明白你的考虑。我们来看怎么落地：目前团队在手的有 A/B/C 三件事，如果要加 D，就需要砍掉或推迟其中一件。你觉得哪个可以放一放？"老板也需要做取舍，只是 TA 需要你帮 TA 看到取舍。
- **Q：怎么让需求方下次变更时更慎重？**
  → 每次变更都公开记录（组会、周报里提一句："本周因为 X 需求变更，B 项目推迟了 3 天"）。不是指责，是让变更的成本可见。需求方发现自己的变更会被记录和传播，下次就会先想清楚再提。
- **Q：团队内部出现了"差不多先生"——自己随意加需求不告诉你怎么办？**
  → 1on1 里聊。问 TA"你当时决定加这个是因为什么考虑？"不是在追责，是帮 TA 建立"变更意识"。IC 的视角常常是"把这个做好只要 1 天，顺手做了呗"，TA 没意识到的是这 1 天挤掉了排期里另一个 1 天。

## 我的记法

- **变更三步骤**：理解真实需求（为什么）→ 量化变更成本（代价多少）→ 给选项让 TA 选
- **永远是 3 个选项**：砍范围、加时间、降质量——让 TA 做取舍
- **你不是传话筒**：你消化外部压力，翻译成团队能执行的方案
- 一句话：**「变更不可怕，可怕的是没代价的变更——每次变更都让人看到成本」**
